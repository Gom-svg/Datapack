# DataPack Release Artifact and Checksum Policy

Status: **CERTIFIED POLICY — Productization P1**

This document defines the public release artifact contract P7 must implement.
P2 implements and certifies platform wheels as temporary GitHub Actions
artifacts; it does not upload, sign, or publish release artifacts.

## 1. Artifact set

For an authorized version `{version}`, the initial release set is:

| Kind | Required filename policy |
| --- | --- |
| Linux x86_64 CLI bundle | `datapack-{version}-x86_64-unknown-linux-gnu.tar.gz` |
| Windows x86_64 CLI bundle | `datapack-{version}-x86_64-pc-windows-msvc.zip` |
| Python ABI3 wheels | Build-standard wheel filename for distribution `datapack-engine`; Linux `datapack_engine-{version}-cp39-abi3-manylinux_2_17_x86_64.manylinux2014_x86_64.whl`; Windows `datapack_engine-{version}-cp39-abi3-win_amd64.whl` |
| Release notes | `datapack-{version}-RELEASE-NOTES.md` |
| Artifact manifest | `datapack-{version}-manifest.json` |
| SHA-256 checksums | `datapack-{version}-SHA256SUMS.txt` |

Wheel filenames are generated by the packaging tool and validated, not manually
renamed. Python distribution normalization (`datapack-engine` to
`datapack_engine`) does not change the `datapack` import package.

P2 builds one wheel per platform and reuses that exact ABI3 wheel across
GIL-enabled CPython 3.9 through 3.14. The Linux policy is glibc 2.17 / manylinux2014.
See `PYTHON_DISTRIBUTION.md` for certification evidence and current limitations.

There is no crates.io `.crate` release artifact in the Productization Foundation
artifact set. `cargo package` remains an internal package-content verification gate.

## 2. CLI bundle contents

Each CLI bundle contains one top-level directory matching the bundle filename
without its archive suffix. That directory contains only:

- `datapack` on Linux or `datapack.exe` on Windows;
- `README.md` with artifact-specific installation and basic safe-use instructions;
- `LICENSE-MIT`;
- `SECURITY.md`; and
- `RELEASE-NOTES.md` for the exact package version.

No source checkout, test dataset, `.dpack` archive, temporary output, benchmark
result, private path, or build cache belongs in a CLI bundle.

## 3. SHA-256 checksum file

Checksums are computed over the final uploaded bytes after all archive/wheel names
and contents are final. `datapack-{version}-SHA256SUMS.txt`:

- uses lowercase hexadecimal SHA-256;
- contains one line per binary bundle, wheel, release-note artifact, and manifest;
- uses the conventional `HASH  FILENAME` form with two ASCII spaces;
- contains base filenames only, never absolute paths;
- is sorted by filename using bytewise ordering;
- contains no self-referential checksum entry; and
- is verified in a clean isolated directory before artifacts are eligible for
  release.

SHA-256 proves downloaded-byte identity with the published checksum set. It is not
publisher authentication. Signing and key management remain deferred until an
explicit trust and key-custody policy is authorized.

## 4. Artifact manifest

`datapack-{version}-manifest.json` is deterministic JSON for the same release
inputs, aside from explicitly recorded build time if one is retained. It contains:

- schema version and report type;
- product name and package version;
- release channel;
- source commit and source ref/tag when authorized;
- Rust/Cargo version and lockfile SHA-256;
- workflow name/run identity;
- one entry per artifact with filename, kind, target/platform, byte size, SHA-256,
  and relevant ABI facts;
- CLI-reported version for CLI bundles;
- Python distribution/import names and ABI tag for wheels; and
- the status of isolated smoke tests.

The manifest does not contain secrets, credentials, runner home paths, source data,
or claims about performance.

## 5. Build provenance and reproducibility boundary

Release artifacts are built by a committed workflow from a committed source ref,
the exact Rust 1.85.0 toolchain, committed lockfiles, and pinned major/action inputs.
The manifest records those inputs. P7 must minimize undeclared runner state and use
release/optimized builds.

This is a reproducible process policy, not yet a claim that two independent builds
produce byte-identical executables or compressed bundles. Byte-for-byte reproducible
builds may be claimed only after independent evidence identifies and controls
timestamps, archive ordering, compiler/linker paths, and platform toolchain inputs.

## 6. Required isolated smoke tests

Before an artifact can be marked supported for a release:

- extract/install it outside the source checkout;
- run the CLI or Python distribution version check;
- exercise a small deterministic v1 round trip and v2 multichunk round trip;
- validate the archives and independently compare restored bytes;
- confirm overwrite protection and failure cleanup;
- verify artifact filenames, bundle/wheel contents, manifest entries, byte sizes,
  and SHA-256 values; and
- ensure no build directory, source fixture mutation, or unexpected artifact is
  tracked.

Smoke tests do not replace the full Rust, Python, dependency, compatibility, and
security gates.

## 7. Publication boundary

P7 may prepare workflow artifacts for review. Creating a public GitHub Release,
publishing `datapack-engine` to PyPI, reserving a registry project, or publishing a
Rust crate requires separate explicit authorization. No workflow may perform those
actions on an ordinary push or pull request.
