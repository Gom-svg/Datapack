## 1. Purpose and audit

P7 makes internal candidate artifacts buildable, identifiable, inspectable, and
verifiable without manual archive assembly. It does not publish DataPack or
change the development version `0.1.0`.

The audit found an established P1 artifact contract, exact product/version
checks, Rust/Cargo 1.85.0, MIT licensing, P2 manylinux2014/Windows ABI3 wheels,
path remapping, a strict eight-member wheel allowlist, isolated installation,
and P6 correctness certification. Existing Actions uploads retain wheels for
14 days. There was no CLI packager, candidate aggregator, manifest generator,
or release workflow. The existing contracts are reused, including P1's versioned
metadata filenames and five-member CLI packages.

The implementation consists of one Python 3.9-compatible, standard-library
release tool, focused tests, a shared wheel-build composite action, and a manual
candidate workflow. It imports the existing wheel certifier and version checker;
it does not fork their checks. The original wheel certifier, installed tests, and
P6 harness are unchanged.

## 2. Artifact contract

The existing `RELEASE_ARTIFACTS.md` remains the naming/content policy. For the
current development version, a complete candidate contains exactly seven files:

| File | Contents / target |
| --- | --- |
| `datapack-0.1.0-x86_64-unknown-linux-gnu.tar.gz` | Linux GNU x86_64 CLI package |
| `datapack-0.1.0-x86_64-pc-windows-msvc.zip` | Windows MSVC x86_64 CLI package |
| `datapack_engine-0.1.0-cp39-abi3-manylinux_2_17_x86_64.manylinux2014_x86_64.whl` | Standard maturin Linux ABI3 wheel |
| `datapack_engine-0.1.0-cp39-abi3-win_amd64.whl` | Standard maturin Windows ABI3 wheel |
| `datapack-0.1.0-RELEASE-NOTES.md` | Internal candidate notes |
| `datapack-0.1.0-manifest.json` | Machine-readable candidate identity and certification records |
| `datapack-0.1.0-SHA256SUMS.txt` | Conventional SHA-256 checksums |

Names use `VERSION`; wheels are generated by maturin, inspected, and never
renamed. A candidate designation is workflow/artifact metadata, not a SemVer
promotion, version bump, or RC tag.

Each CLI archive contains one directory named after the archive without its
suffix. It contains exactly `datapack` or `datapack.exe`, `README.md`,
`LICENSE-MIT`, `SECURITY.md`, and `RELEASE-NOTES.md`. License and security text
match the source. The two usage/note templates in `docs/releases/` substitute
only `@VERSION@`. Archives contain no source tree, sample data, logs, or tests.
Narrow `.gitattributes` rules retain LF bytes for these documents, the wheel
license copy, and both hashed lockfiles on Linux and Windows. This prevents
checkout newline conversion from changing cross-platform document comparisons
or source-provenance hashes; their committed contents are unchanged.

Linux uses a normalized USTAR archive and gzip header with timestamp zero.
Members have fixed ownership, sorted names, and modes 0755 for the executable
and 0644 for documents. ZIP members have fixed 1980 timestamps, regular-file
attributes, and sorted names. Tests demonstrate repeat packaging of identical
inputs; they do not establish independent compiler or wheel reproducibility.

## 3. Integrity and provenance

The checksum file uses lowercase SHA-256 and `HASH  FILENAME`, sorted by filename.
It covers both CLI archives, both wheels, notes, and the final manifest. It does
not checksum itself. Generation reads the final files; verification recomputes
every hash and rejects missing, extra, reordered, or altered entries. The hosted
aggregation job additionally runs the independent `sha256sum --check` command.

The schema-1 manifest is canonical JSON: sorted keys, two-space indentation,
ASCII escaping, and a final newline. It records:

- `schema_version`, `report_type`, product, `version`, and `channel`;
- `source.commit`, `source.dirty`, and SHA-256 values of the core and binding
  lockfiles;
- exact `rustc`/`cargo` toolchain versions and `python_abi`;
- workflow name, run ID and attempt, or an explicit local workflow identity;
- platform runtime observations; and
- sorted artifact entries with filename, kind, target, byte size and SHA-256,
  plus CLI version or wheel distribution/import/ABI/tags and smoke PASS status.

The manifest lists the four distributables and notes, excluding itself and the
checksum file to avoid circular hashes. No timestamps, usernames, absolute paths,
credentials, or logs appear in it. Workflow identity intentionally distinguishes
different executions; deterministic serialization does not equate different
workflow runs.

Each platform job writes a separate internal `certification.json` only after its
packaged CLI and wheel have passed. It binds artifact sizes/hashes and smoke
status to the source, lockfiles, toolchain, workflow run/attempt, and platform.
Aggregation requires exactly one record per platform with matching provenance
and unchanged artifact bytes. These records are retained as platform job output
but excluded from the final seven-file candidate bundle.

The workflow checks out `github.sha`, and the tool compares it with `git HEAD`.
Clean-source builds are the default. `--allow-dirty` is an explicit local rehearsal
mode, recorded as such; it is forbidden in Actions, and dirty source records
cannot be assembled into a candidate. Local rehearsals are useful for validating
packaging changes before committing them, but are not clean-commit provenance.
The runtime version output is unchanged. Commit identity belongs to release
metadata, not the public API or CLI version string.

Checksums and records are integrity/provenance metadata within the trusted build
workflow, not cryptographic publisher authentication. They do not prove that a
malicious builder reported honestly. Signing, GitHub attestations, OIDC write
permissions, SLSA claims, notarization, and external supply-chain audits are
deferred; they are unnecessary for this baseline.

## 4. Workflow and build reuse

`.github/workflows/release-candidate.yml` supports `workflow_dispatch` and
`workflow_call` with `contents: read`; its platform jobs require a manual dispatch
event, including when called. It has two native platform jobs and one dependent
aggregation job, not another broad 18-job compatibility matrix.

Each platform checks product identity, runs release-tool tests, uses the shared
wheel build, builds the CLI with Rust/Cargo 1.85.0 and locked dependencies,
packages and extracts the CLI, certifies both artifacts, and uploads its validated
platform output. The Linux CLI runs on `ubuntu-24.04`; the Windows CLI is built
and executed on `windows-latest` with MSVC.

`.github/actions/build-python-wheel/action.yml` holds the proven pinned maturin
1.14.1 action/build and exact wheel inspection steps. Both the existing CI and
P7 call it. Linux retains the manylinux2014 container and auditwheel check;
Windows retains the native MSVC build. The existing CI still expands its five
job groups to 18 jobs with the same targets, six Python minors, test harnesses,
policy gates, and 14-day wheel uploads. Only the wheel-build implementation is
shared. CI also gains a boolean `release_candidate` manual input, default false,
and a conditional call to the dedicated P7 workflow. Pushes, pull requests, and
ordinary manual CI runs still execute the existing 18 required jobs. An explicit
candidate invocation skips that compatibility matrix and calls only the three
P7 jobs. This routing is a P7 workflow addition; it does not weaken any normal CI
gate. The manifest records the actual caller name (`CI` or `Release Candidate
Artifacts`) with its run ID and attempt.

The aggregator depends on successful completion of both platform jobs. It
downloads only the two outputs from the current run, rejects incomplete or
inconsistent records, inspects all packages again, assembles in a temporary
directory, verifies the manifest/checksums, copies the final bundle, verifies
again, and uploads only after independent checksum verification succeeds.
There are no `always()` uploads of the final candidate.

Platform and final bundle uploads use 14-day retention and no extra compression.
The final Actions artifact name is `datapack-candidate-bundle-<source SHA>`.
Actions storage is temporary evidence, not permanent distribution. There is no
GitHub Release, registry upload, tag creation, signing, or publication step.

## 5. Artifact acceptance

CLI inspection checks the canonical filename, exact five-member allowlist,
normalized metadata, document bytes, and executable header/architecture. Links,
duplicates, unexpected paths/files, and oversized members are rejected before
writing extracted files. Extraction writes only validated allowlisted names.

The smoke executes the extracted binary outside the checkout with a restricted
runtime PATH. It checks exact `datapack <VERSION>`, help, small deterministic V1
and V2 multichunk compression, source-aware validation, decompression, byte and
SHA-256 equality, overwrite rejection, and malformed-input failure cleanup.
The approximately 2 MiB fixture exists only in the temporary smoke directory.

Wheel certification invokes the unchanged `certify_python_wheel.py` functions:
exact standard name/tags, metadata, license and eight-member allowlist; then an
isolated venv, `--no-index --no-deps` install, public SDK tests, and the P6 CI
profile. Repository source is absent from runtime import paths; Rust, Cargo, and
maturin are absent from runtime PATH. PEP 561 and stubs remain mandatory.
P7 exercises each exact wheel on CPython 3.14. P6/current CI provide the broader
CPython 3.9–3.14 compatibility matrix; P7 does not claim to rerun it.

Build remapping preserves P2's source/home/container mappings and extends them
to temporary directories. CLI release symbols are stripped. P7 scans extracted
CLI members, wheel members, and metadata with the existing P2 sensitive/path
rules plus temporary/runner paths and UTF-16 representations. No existing leak
check is disabled.

Linux CLI runtime metadata records the highest `GLIBC_*` version string found
in the binary and the host libc version used for smoke execution. These are
observations, not certification on every older distribution or a complete shared
library dependency inventory. The wheel's glibc 2.17 contract is separate from
the native CLI's host build. Windows support requires the hosted MSVC artifact
and extracted executable to pass on Windows; WSL cannot provide that evidence.

## 6. Local use

From a clean matching checkout, use a supported native x86_64 host, Rust/Cargo
1.85.0, and CPython with venv/pip support. Install build-only tools into a separate
environment; no runtime dependency is added to DataPack:

```bash
python3 -m venv /path/to/build-venv
/path/to/build-venv/bin/python -m pip install 'maturin[zig]==1.14.1' 'ziglang==0.16.0'
export CARGO_TARGET_DIR="$HOME/.cache/datapack-modernization"
/path/to/build-venv/bin/python scripts/release_candidate.py build \
  --platform linux --out dist/linux
```

Linux local wheel builds use the existing Zig/manylinux2014 auditwheel strategy.
On native Windows with an MSVC build environment:

```powershell
python -m venv C:\build-venv
C:\build-venv\Scripts\python -m pip install maturin==1.14.1
C:\build-venv\Scripts\python scripts/release_candidate.py build --platform windows --out dist/windows
```

The tool builds the CLI and a fresh wheel, certifies both, and writes the platform
directory only after passing. Output directories must not already exist. Use a
new directory for a new run. `--wheel-dir` is restricted to the shared wheel
built earlier in the same hosted job; local builds do not relabel an arbitrary
old wheel as a fresh-source build.

For development before committing, add `--allow-dirty` and use a separate output
directory. This produces a clearly marked local rehearsal; it cannot be combined
into a complete candidate. Build again from a clean reviewed commit for candidate
provenance. Local output under `/dist/` is ignored, and no artifact belongs in Git.

After collecting both **local**, clean-source platform directories from the same
commit and lockfiles, assemble from that matching clean checkout:

```text
python scripts/release_candidate.py assemble --platform-dir dist/linux --platform-dir dist/windows --out dist/candidate --expected-commit <full source SHA>
python scripts/release_candidate.py verify --bundle dist/candidate --expected-commit <full source SHA>
```

The full verifier requires the matching clean source checkout to compare package
documents, identity policy, and lockfiles. It accepts valid hosted provenance when
verifying a downloaded bundle locally. A recipient can independently verify
downloaded byte integrity without Python or source using `sha256sum --check` on
Linux, or compare `Get-FileHash -Algorithm SHA256` values on Windows against the
six conventional checksum entries.
